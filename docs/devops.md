# DevOps and Operations

Practical guidance on building, testing, developing, and releasing `support.java`.

---

## Prerequisites and Environment
- JDK: Java 25, auto-provisioned by the Gradle toolchain if not already installed locally.
- Gradle: Gradle 9.7.0, managed via the included wrapper (`gradlew` / `gradlew.bat`).
- Python 3: runs the scripts under [scripts](../scripts); they use only the standard library.
- Git: Git 2.30+ supporting worktrees (`git worktree`).
- GitHub CLI: `gh`, logged in, for releases only.
- Docker: only needed to run `SqlPagingTest` (a Testcontainers-backed MariaDB integration test); it's skipped,
  not failed, when Docker is unavailable.
- PowerShell / Bash: PowerShell on Windows (`gradlew.bat`), standard POSIX shell on macOS/Linux (`./gradlew`).
- GitHub Packages credentials: `github.username` and `github.token` (a personal access token with
  `write:packages`) in `${user.home}/.gradle/gradle.properties`, or the `GITHUB_USERNAME` and `GITHUB_TOKEN`
  environment variables. These stay outside version control. See
  [Configuring Gradle for GitHub Packages](https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-gradle-registry).

## Development Workflows

### Initial Bootstrap
```bash
python scripts/bootstrap-dev-environment.py
```
Initializes git if needed and runs `gradlew build` (`gradlew.bat` on Windows, `./gradlew` on POSIX). No
`deploy-to-production.py` is provided: this is a library published to a package repository, not a deployed
service.

### The devops.py Runner
[devops.py](../scripts/devops.py) is the single entry point for typical operations:
```bash
python scripts/devops.py help --verbose       # every action, option, and exit code
python scripts/devops.py check                # what CI runs: Spotless, Checkstyle, tests, jars (gradlew build)
python scripts/devops.py test --tests "com.pellicciotta.support.text.TokenizerTest"
python scripts/devops.py versions             # gradle.properties and CHANGELOG.md must agree
python scripts/devops.py release --dry-run    # preview the release pipeline
```
CI runs `devops.py check`, so a local `check` passing means CI will pass.

### Building and Testing
```powershell
# Compile main sources only
.\gradlew.bat compileJava

# Full compile, format and style checks, test, and jar/javadoc-jar/sources-jar assembly
.\gradlew.bat build

# Run all tests (streams stdout live per test - see testLogging in build.gradle)
.\gradlew.bat test

# Run a single test class
.\gradlew.bat test --tests "com.pellicciotta.support.text.TokenizerTest"

# Run a single test method
.\gradlew.bat test --tests "com.pellicciotta.support.text.TokenizerTest.testSomething"

# Run the Docker-backed database integration test
.\gradlew.bat test --tests "com.pellicciotta.support.sql.SqlPagingTest"
```
`SqlPagingTest` starts and tears down its own MariaDB automatically via Testcontainers — no hand-run server or
manual setup needed; its `@BeforeAll` creates the `test` database and `score` table (via
`src/test/resources/sql/mysql/setup-db.sql`) inside the container. Docker must be running; if it isn't,
`@Testcontainers(disabledWithoutDocker = true)` reports the class as skipped rather than failed.

### Dependency Versions
All dependency and plugin versions live in [libs.versions.toml](../gradle/libs.versions.toml). Dynamic versions
such as `1.+` are not used, so builds resolve the same artifacts everywhere.

### Task Tracking
Tasks live in [PLAN.md](../PLAN.md) and `.plan/tasks/` and are managed only through the `plan` CLI (`plan help`).
Never edit `PLAN.md` or task frontmatter by hand.

### IntelliJ Gradle Import
If IntelliJ doesn't pick up Gradle dependencies automatically: `View > Tool Windows > Gradle`, then hit
"Refresh". The module files are generated by that import and are not committed.

## Release Process
Ongoing work accumulates under the top `CHANGELOG.md` heading while it carries a `-pre` SemVer suffix (e.g.
`## v1.0.0-pre`), which must always match `version` in `gradle.properties` (the single source of truth for the
jar manifest and Maven coordinates) exactly, `-pre` included. Escalate that heading and version together — to
the next major, minor, or patch number — the moment a change lands that needs it. A breaking change escalates
to the next major.

### Releasing with doFullRelease
```bash
python scripts/devops.py release --dry-run   # list the Gradle tasks the pipeline would run
python scripts/devops.py release             # asks for a typed confirmation, then releases
```
The same pipeline runs directly as `.\gradlew.bat doFullRelease -PreleaseConfirmed=yes`. Without that property it
refuses to start, because it publishes packages and pushes to origin. In order, it runs:
- `checkReleasePreconditions` — full `build`; then fails unless the confirmation was given, the working tree is
  clean, the branch is `master`, `version` ends in `-pre`, `CHANGELOG.md` has the matching heading, `gh` is
  logged in, HEAD equals `origin/master`, and CI is green for HEAD (it waits up to 15 minutes for a running build).
- `finalizeRelease` — strips `-pre` from `gradle.properties`, marks the heading `[released: {{date}}]`, commits.
- `publishReleaseArtifacts` — publishes to GitHub Packages in a nested Gradle run, so it uses the released version.
- `tagAndPushRelease` — tags `v{{version}}`, pushes the branch and the tag.
- `createGithubRelease` — creates the GitHub Release with the changelog section as notes.
- `openNextPreRelease` — bumps to the next patch `-pre`, opens its changelog heading, commits, and pushes.

Any task can be run on its own (for example `.\gradlew.bat checkReleasePreconditions -PreleaseConfirmed=yes`) to
diagnose or resume a failed release without repeating the steps already done.

**Never run a release unless explicitly asked.** It publishes to a shared repository that other repos depend on.

### Publishing Details
Publishing SNAPSHOT versions does not work reliably against GitHub Packages (first publish succeeds, subsequent
publishes and consumption fail with a 400 on `maven-metadata.xml`), so this project does not use SNAPSHOT
versions. The publication, POM metadata, and repository are configured in [build.gradle](../build.gradle).

## Continuous Integration
The GitHub Actions workflow in [ci.yml](../.github/workflows/ci.yml) triggers on push and pull requests, executing:
- Java JDK 25 setup (Temurin distribution).
- `python3 scripts/devops.py check` (formatting, style, compilation, unit and integration testing, and packaging).
  GitHub-hosted `ubuntu-latest` runners ship Docker, so the Testcontainers-backed `SqlPagingTest` runs in CI too.
